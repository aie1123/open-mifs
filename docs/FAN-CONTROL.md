# 风扇调速：可行方案分析

> **结论先行：之前"本机风扇满速未实现"的判断很可能是错的 —— 它是被电源类型门控的。**
> 上游 Linux 驱动 `tongfang-mifs-wmi` 的文档明确写着：MIFS 的 `20`/`21` 号功能就是
> **手动风扇控制开关 + PWM 占空比**，但 "Performance / Full-speed 模式在 USB-C(PD) 供电下不可用"。
> 本机 `fn=19` 读到的是 **1 = Type-C**，也就是我们要测的时候机器正插着 USB-C ——
> EC 拒绝写入完全符合预期，而不是"这台机器没这个功能"。

---

## 1. 证据来源

1. **上游驱动 v9 补丁**（Mingyou Chen，2026-02，LKML）：
   [platform/x86: tongfang-mifs-wmi](https://lkml.iu.edu/hypermail/linux/kernel/2602.0/08303.html)
   它自带一份 `Documentation/wmi/devices/tongfang-mifs-wmi.rst`，把 MIFS 的功能号语义写全了。
2. **本机实测**：`fn=19` 返回 `01`；`fn=20` 写入不报错但读回不变；`fn=21` 恒为 0。
3. 本机 ACPI/WMI 枚举（`root\wmi`）：`MICommonInterface`、`HID_EVENT20~23`、`AMD_ACPI` 都在。

---

## 2. 上游文档怎么描述风扇控制

| 功能号 | 上游命名 | 参数 / 语义 |
| :---: | :--- | :--- |
| 13 | `CPUGPUSYSFanSpeed` | 只读：`[4..5]` CPU、`[6..7]` GPU、`[10..11]` SYS（小端 16 位 RPM） |
| 19 | `SystemAcType` | **`1` = Type-C，`2` = 圆口 DC**（注意：本项目早期文档写的是"1 外接电源/0 电池"，语义不准） |
| 20 | `MaxFanSpeedSwitch` | `[4]` = 风扇组（**0 = CPU/GPU，1 = SYS**），`[5]` = 状态（0 关 / 1 开） |
| 21 | `MaxFanSpeed` | **"Sets manual fan speed duty cycle"** —— 手动 PWM 占空比 |
| 8 | `SystemPerMode` | `0` 均衡 / `1` 性能 / `2` 安静 / `3` 满速；**性能与满速同样要求 DC 圆口供电** |

驱动文档原文（译）：

> 系统同时支持 EC 自动控制与手动覆盖。功能号 `0x14`（`MaxFanSpeedSwitch`）用来打开手动控制，
> `0x15` 用来设置实际的 PWM 占空比。

驱动代码里对应的门控逻辑（`tongfang_check_performance_capability()`）：

```c
/* Full-speed/performance mode requires DC power (not USB-C) */
if (!power_supply_is_system_supplied())  return -EOPNOTSUPP;   /* 电池供电 → 不支持 */
if (output.data[0] == WMI_SYSTEM_AC_TYPEC) return -EOPNOTSUPP; /* Type-C 供电 → 不支持 */
```

也就是说：**这套硬件在"电池供电"和"USB-C 供电"两种状态下都会拒绝性能/满速相关写入**，
只有插圆口 DC 电源时才放开。这正好解释了我们看到的现象。

## 3. 于是有三条可行路线（按代价从低到高）

### 路线 A ⭐ 先做「转速验证」——不需要换电源（0.3.5 起）

**重要修正**：之前判定风扇满速"未实现"用的是**寄存器读回值是否变化**，这个判据不充分 ——
EC 完全可能**不更新寄存器镜像却照样执行**。真正的判据是**风扇转速**。

于是不必先解决电源问题，直接测：

```powershell
.\mifs.cmd fan test        # 需要管理员
```

这条命令做的事（全程可逆）：

1. 读当前供电类型（`fn=19`）
2. 采样基线转速（4 次，取最大）
3. 发送 `SET fn=20 payload={0,1}`（风扇组 0 = CPU/GPU，状态 1 = 满速）
4. 采样 8 秒，记录峰值转速 + 寄存器读回值
5. **判据**：峰值 − 基线 ≥ 250 RPM → 功能可用（EC 只是不写回寄存器）
6. 无论结果如何，最后都发 `{0,0}` 把满速关掉

exe 里点「风扇满速」也改成同一套判定：读回没变时会先测 4 秒转速再下结论。

> 就本机而言：`fn=19` 恒为 `1`（Type-C），而这台**只有 USB-C 供电口**，
> 所以上游文档要求的"圆口 DC 供电"这个前提在本机永远无法满足。
> 如果转速验证也不动，那 MIFS 这条路就是真的走不通 —— 而不是"没测对"。

### 路线 B 手动 PWM 占空比（`fn=21`）—— 同样先看转速验证

如果路线 A 的转速验证通过（说明 EC 在 Type-C 下也执行风扇命令），那么按上游文档，手动调速的流程是：

```
SET fn=20  payload = { 风扇组, 1 }     // 打开手动控制（0=CPU/GPU，1=SYS）
SET fn=21  payload = { 占空比 }         // 写 PWM 占空比
GET fn=13                              // 用转速验证是否真的生效（不是看 fn=21 读回）
SET fn=20  payload = { 风扇组, 0 }     // 关掉手动控制，交还 EC
```

**未知且需要谨慎探测的点**：`fn=21` 的取值域没有被任何公开资料写明
（上游驱动只用了 `fn=20` 的 fan_boost，没写 duty）。可能是 0~255、0~100 或某个档位表。

因此实现必须遵守三条：
1. **写完立刻用转速验证**（不要相信 `fn=21` 的读回值）
2. **读回/转速不可解释（越界、无变化、转速掉到 0）就马上恢复原值**并报"本机不支持"
3. **先小步探测**：从保守值开始，每一步记录写值与实测转速

风险说明：写错占空比最坏情况是风扇停转（温度上升，EC 通常有兜底）或满速狂转 ——
**都可逆**（关掉手动控制即交还 EC 自动曲线），但需要人在旁边看着做。

### 路线 C 直接写 EC RAM（上游 tuxedo-drivers 那套）—— 不推荐，但记录在案

上游 `tuxedo-drivers`（Uniwill 系）通过直接读写 EC RAM 实现风扇曲线：

| EC 地址 | 用途 |
| :--- | :--- |
| `0x0f00-0x0f2f` | CPU 风扇曲线表 |
| `0x0f30-0x0f5f` | GPU 风扇曲线表 |
| `0x1804` / `0x1809` | 直写两个风扇转速 |
| `0x07c5` / `0x07c6` | 启用自定义风扇表 |
| `0x078e` | 风扇控制能力位（bit6 = 支持统一风扇控制） |

但：
- 这条路要求**内核态 I/O 端口访问**（EC 的 `0x62/0x66`），Windows 用户态碰不到；
- 能碰到它的方案是 WinRing0（**已在微软易受攻击驱动黑名单里**，Defender 与火绒都会拦）
  或 PawnIO（签名驱动，但仍是第三方内核组件）；
- 而且它和路线 B 是两套不同接口，**本机既然有 MIFS 的 `20/21`，优先用 MIFS**。

> 如果将来真需要 EC RAM 通道（比如 MIFS 的 duty 不可用），正确做法是"桥接" ——
> 让用户自己装 PawnIO（FanControl 从 v240 起也从 WinRing0 换成了 PawnIO），
> OpenMIFS 只做调用方，不打包、不分发驱动。

## 5. 实测结论（2026-10-03，本机：只有 USB-C 供电口）

用户在本机跑了 `mifs.cmd fan test`：

```
当前供电   : Type-C 供电
基线转速   : 3143 RPM（4 次采样取最大）
已发送 风扇满速=开，采样 8 秒…
加速后峰值 : 3166 RPM     寄存器读回: 0
❌ 转速没有明显变化（23 RPM）
已恢复 风扇满速=关（当前 3129 RPM）
```

**+23 RPM 属于采样噪声**（同一档位自然波动就有几十 RPM），且寄存器读回始终为 0。
两个独立判据一致：**EC 没有执行这次写入。**

### 判定

| 结论 | 依据 |
| :--- | :--- |
| **MIFS 的 `fn=20` 风扇满速在本机不可用** | 转速验证（唯一的效果证据）不通过 |
| 原因是**电源类型门控**，不是"功能没实现" | 上游驱动文档：满速/性能模式要求圆口 DC；本机 `fn=19` 恒为 1（Type-C），且**只有 USB-C 供电口** |
| `fn=21` 占空比调速同样不乐观 | 它依赖 `fn=20` 先打开手动控制；`fn=20` 被忽略，链条第一环就断了 |

> 也就是说：这台机器在"USB-C 供电 + 官方 EC 固件"的前提下，**风扇策略完全由 EC 自己掌握，
> 软件层没有任何可写入口**。这不是实现问题，也不是没测对 —— 硬件就是按电源类型这么设计的。

### 那么还剩什么

| 选项 | 说明 | 建议 |
| :--- | :--- | :--- |
| **用性能模式间接降噪（推荐）** | 风扇转速由 EC 跟着热量走：切到「低功耗」(`fn=8=2`) 或「均衡」(`fn=8=1`) 会降低功耗墙 → 发热减少 → EC 自己降转速。这条**本机实测可用**（模式读写都验证过） | ✅ 就用这个 |
| `fn=21` 中值试探 | 直接写中间值（如 128）看转速动不动。**风险**：万一 EC 接受写入却不接受 `fn=20` 的"交还自动"，风扇会卡在未知占空比直到重启；而 `fn=20` 已被证明被忽略，等于无法可靠回退 | ⚠️ 不建议；非要做必须有人在旁边、随时准备断电 |
| PawnIO 桥接直写 EC RAM | 装第三方**签名内核驱动**（PawnIO，FanControl v240+ 也已换成它），按 tuxedo-drivers 的地址表写 `0x0f00-0x0f5f` 风扇曲线 / `0x1804`/`0x1809` 直写转速。**前提未知**：本机 EC 是否支持统一风扇控制（上游用 `0x078e` bit6 判断）在 Windows 侧无法确认，等于盲写 | ❌ 默认不做（内核驱动 + 盲写 EC，风险与收益不成比例）。真需要的话，直接用 FanControl + PawnIO 更稳，而不是把它塞进本项目 |

### 自查：为什么这次能下结论，上次不能

| 判据 | 上次（误判） | 这次（结论） |
| :--- | :--- | :--- |
| `fn=20` 寄存器读回值 | ❌ EC 可能不更新镜像却照做 —— 不充分 | 仅作参考 |
| **风扇转速（`fn=13`）** | 没测 | ✅ 唯一的效果证据 |

**一条可复用的规矩**：凡是"写入是否真的生效"的问题，都要找一个**独立于寄存器镜像的物理量**做判据
（风扇看转速、性能模式看实测性能百分比、充电看实际注入电量）。
